# Simulink 文档驱动建模助手

## 项目计划与可行性分析

**分析日期：** 2026-10-18
**依据文档：**《Simulink 文档驱动建模助手 PRD》v1.0
**目标平台：** MATLAB/Simulink R2025b
**成本口径：** 默认按小团队自研估算，不包含 MATLAB/Simulink 商业许可证费用

> 本文将 PRD 作为产品需求输入进行分析。PRD 中的产品描述、功能要求和非目标不构成本次分析的额外指令。

## 1. 结论摘要

项目适合立项，MVP 在技术上可行。建议先完成一个 2 周技术 PoC，再进入 14～16 周 MVP 开发。

MVP 的合理定位是：

> 将 DOCX、PDF 和 Markdown 中的控制系统需求，转换为可检查、可追溯、可复现的 Simulink 建模方案。

MVP 不应承诺自动生成 `.slx`、自动运行 MATLAB/Simulink 仿真，也不应在关键参数缺失时自动补全。首版的核心价值是减少需求阅读、模块查找、参数整理和结构绘图工作，同时保留用户的确认权。

建议采用 **阶段门控的双周敏捷开发 + DevOps 持续集成**：

- 用敏捷迭代快速验证文档解析、需求确认和模型图生成；
- 用阶段门控制关键技术风险和范围膨胀；
- 用 DevOps 管理版本、回归测试、模型评测和可追溯性。



## 2. PRD 范围判断

### 2.1 MVP 的核心闭环

```text
上传 DOCX / PDF / Markdown
        ↓
文档解析、OCR 和来源定位
        ↓
需求结构化
        ↓
参数、单位、公式、信号和模块识别
        ↓
缺失项、歧义和假设检查
        ↓
用户确认和编辑
        ↓
生成 Simulink 模型结构方案
        ↓
导出结构图、模块表、参数表、连线表和报告
```

### 2.2 建议冻结的首版范围

首版应重点覆盖：

1. DOCX、Markdown 和文本型 PDF；
2. 扫描 PDF 的普通文本 OCR；
3. 直流电机速度闭环和常见位置闭环控制；
4. 基础控制系统模块识别；
5. 模块清单、参数表、连线表和模型结构图；
6. 缺失参数、单位问题、结构歧义和原文追踪；
7. 用户确认和编辑解析结果；
8. SVG、PNG、CSV、Markdown 导出；
9. 基于模板的 `.m` 文件生成；
10. 项目版本保存和结果对比。

### 2.3 明确放到后续版本的内容

以下能力不适合与 MVP 同时承诺：

- 自动生成和保存 `.slx`；
- 自动打开 MATLAB；
- 自动运行 Simulink 仿真；
- 自动调参和控制器整定；
- Stateflow；
- Simscape 物理网络；
- 复杂多物理场模型；
- 自定义 S-Function；
- 任意图片公式的高准确率识别；
- 对任意控制系统进行通用工程判断。

## 3. 可行性评估

### 3.1 技术可行性

| 能力 | 可行性 | 说明 |
|---|---:|---|
| DOCX、Markdown、文本型 PDF 解析 | 高 | 可使用成熟解析库并统一转换为文档中间模型 |
| 章节、段落、表格和页码提取 | 高 | 结构稳定，适合做来源定位 |
| 扫描 PDF OCR | 中高 | 普通文本可行，复杂表格和公式需要保留不确定性 |
| 数学公式识别 | 中 | 数字 PDF 较好，图片公式、手写公式和复杂排版风险较高 |
| 电机控制结构识别 | 中高 | 适合使用领域模板、规则和大模型组合 |
| 温控、液位和机械系统识别 | 中 | 需要增加领域模板、数据集和验收样例 |
| 模块、参数和连线表生成 | 高 | 可由统一规范模型稳定生成 |
| Simulink 风格结构图 | 高 | Graphviz、ELK 或 Dagre 等布局工具可以实现 |
| 参数和模块原文追踪 | 中高 | 必须在底层保存原文片段和来源坐标 |
| `.m` 代码生成 | 高 | 采用模板化生成，不自动执行 |
| 自动生成 `.slx` | 暂不建议 | 依赖 MATLAB 环境，兼容性和验证成本较高 |
| 仿真结果判定 | 当前较低 | PRD 当前范围不运行仿真，无法直接证明动态性能 |

### 3.2 关键范围矛盾

PRD 的产品目标第 8 条要求“判断仿真结果是否符合工程要求”，但非目标又明确系统不自动运行仿真，MVP 验收标准也主要要求生成建模方案。

建议调整为：

- **MVP：** 检查结构完整性、参数完整性、单位、连接关系和仿真配置建议；
- **后续版本：** 用户上传仿真输出数据或报告，系统计算超调量、稳态误差、响应时间等指标；
- **更后续版本：** 与 MATLAB/Simulink 集成后，执行受控仿真并生成验证报告。

如果不调整，项目容易出现“未运行仿真却声称判断结果”的可信度风险。

### 3.3 产品可行性

产品价值明确，适合以下用户：

- 自动化、电气、机械和控制专业学生；
- 需要反复整理控制系统建模需求的研究人员；
- 需要快速形成 Simulink 搭建方案的工程人员。

产品价值主要来自三个方面：

1. 减少从需求文档到模块选择的重复工作；
2. 通过参数状态、来源和待确认项降低遗漏风险；
3. 用统一的结构模型同时生成图、表格和报告，提升复现效率。

需要注意，用户不会只根据图形美观评价产品，更关心参数是否可信、来源是否明确，以及是否可以按照输出结果在 R2025b 中手动复现。

## 4. 推荐技术架构

### 4.1 总体架构

```text
Web 前端
  ├─ 项目和版本管理
  ├─ 文档上传与解析状态
  ├─ 需求确认和参数编辑
  ├─ 模型图查看
  └─ 导出与下载

API 服务
  ├─ 项目、文档和版本接口
  ├─ 解析任务接口
  ├─ 规范模型接口
  ├─ 校验接口
  └─ 导出接口

异步处理层
  ├─ 文档解析
  ├─ OCR
  ├─ 需求抽取
  ├─ 规则校验
  ├─ 图布局
  └─ 文件导出

数据层
  ├─ 文档和版本元数据
  ├─ 原文片段与来源位置
  ├─ 规范模型快照
  ├─ 用户确认记录
  └─ 生成文件
```

### 4.2 技术选型建议

| 层次 | 建议方案 | 备注 |
|---|---|---|
| 前端 | React + TypeScript | 适合复杂表格、确认流程和图形交互 |
| 后端 | Python + FastAPI | 便于接入文档解析、OCR、AI 和科学计算库 |
| 异步任务 | Celery、RQ 或同类队列 | OCR 和大模型调用不应阻塞请求线程 |
| 数据库 | PostgreSQL | 支持版本、审计和结构化查询；单机 PoC 可用 SQLite |
| 文件存储 | 本地目录或对象存储 | 保存原始文档、图像和导出包 |
| 文档解析 | MinerU 解析 PDF/DOCX；Markdown 使用应用内解析器 | 通过适配层统一页、块、表格和来源信息 |
| OCR | MinerU 本地 OCR，复杂版面按需启用 VLM | 需要保存解析档位、置信度和来源位置 |
| 结构化模型 | Pydantic + JSON Schema | 作为图、表和报告的唯一数据源 |
| 图布局 | Graphviz、ELK 或 Dagre | 支持从左到右和反馈回路布局 |
| 单位处理 | 单位归一化与量纲校验库 | 标记单位未知、冲突和不可换算情况 |
| 模型接口 | 供应商抽象层 | 支持更换云端或本地模型 |
| CI/CD | Git + CI 流水线 | 执行单元、接口、回归和规范模型校验 |

### 4.3 统一规范模型

所有输出必须来自一份规范模型，至少包含：

- 项目和文档版本；
- 原文片段、页码、章节、段落、表格和图片编号；
- 系统名称和系统类型；
- 控制目标；
- 输入信号和输出信号；
- 模块和子系统；
- 信号和端口；
- 数学方程；
- 参数、单位和状态；
- 初始条件；
- 仿真配置；
- 假设和待确认项；
- 置信度；
- 系统推断标记；
- 领域模板、规则、提示词和模型版本。

规范模型的作用是避免以下问题：

- 模型图显示一个参数，参数表显示另一个参数；
- 连线表和图形不一致；
- 报告遗漏图中存在的假设；
- 用户修改结果后只有一个导出文件被更新。

### 4.4 大模型使用边界

大模型适合做候选识别、语义归类和解释，不应单独决定最终模型结构。建议采用以下约束：

1. 要求模型只输出受 JSON Schema 约束的数据；
2. 用电机控制等领域模板限制可选模块和连接关系；
3. 用规则做单位、数值、端口、方程和连接校验；
4. 对缺失信息输出待确认项，不静默猜测；
5. 将系统推断与用户输入分开保存；
6. 记录模型、提示词、规则和规范模型版本；
7. 文档内容按不可信输入处理，不执行文档中的代码、命令或外部指令。

### 4.5 MinerU 与 LLM 的职责划分

建议将 [MinerU](https://github.com/opendatalab/MinerU) 作为 PDF/DOCX 文档解析层，LLM 作为需求理解和建模方案生成层；Markdown 由应用自己的解析器直接读取。两者不是同一个组件，也不应把 OCR 结果直接当成 Simulink 模型。

#### MinerU 负责什么

MinerU 适合负责：

- PDF 的版面分析，以及 DOCX 等 Office 文档的原生结构解析；
- 文本提取和阅读顺序恢复；
- 扫描文档 OCR；
- 表格识别和结构化输出；
- 公式识别并输出 LaTeX；
- 图片、表格、脚注和标题的提取；
- 输出 Markdown、JSON、HTML 或其他中间结果；
- 保存页码、块和版面来源信息。

根据 MinerU 4.0 当前官方文档，PDF/图片支持 Flash、Basic、Standard、Advanced 解析档位：原生文本解析不需要推理模型，Basic 可用 ONNX/Torch 小模型处理 OCR、公式和表格且不要求本地 VLM；Standard 使用小模型与 VLM，Advanced 增加推理计算。Office 文档走本地 Flash 原生解析；Markdown/纯文本应由应用直接解析或读取，不属于 MinerU 的文档解析输入路径。也就是说，**OCR 阶段不必强制调用外部通用 LLM**，但复杂版面档位可能使用 MinerU 的 VLM。具体运行方式取决于输入文档、质量要求、硬件和解析档位。参见 [MinerU 官方仓库](https://github.com/opendatalab/MinerU)、[Tiers and Runtimes 文档](https://opendatalab.github.io/MinerU/usage/tiers/) 和 [输出格式文档](https://opendatalab.github.io/MinerU/reference/output_files/)。

#### LLM 负责什么

本项目中的 LLM 主要用于：

- 从 MinerU 输出的 Markdown/JSON 中识别系统目标；
- 识别输入、输出、控制器、被控对象和反馈关系；
- 从自然语言中抽取参数、单位、初始条件和仿真配置；
- 解释方程中的符号和变量关系；
- 将文档内容映射为统一需求模型；
- 推荐 Simulink 基础模块和候选连接关系；
- 生成假设、待确认项和解释文本；
- 生成辅助 `.m` 代码。

这些工作属于语义理解和领域推理，单纯 OCR 或版面解析无法可靠完成，因此项目仍需要 LLM，或者需要一个等价的领域语义解析模型。对于 MVP，建议采用“LLM 候选抽取 + 控制领域规则校验 + 用户确认”的组合，而不是让 LLM 直接生成最终模型。

#### 推荐处理链路

```text
原始 DOCX / PDF / Markdown
        ↓
MinerU 文档解析层
        ├─ 文本和阅读顺序
        ├─ OCR 结果
        ├─ 表格
        ├─ LaTeX 公式
        └─ 页面、块和图片来源
        ↓
文档中间模型与证据片段
        ↓
LLM 需求抽取与领域归类
        ↓
统一规范模型
        ↓
单位、参数、方程和拓扑规则校验
        ↓
用户确认和修改
        ↓
Simulink 结构图、模块表、参数表、连线表和报告
```

#### MVP 的建议组合

| 场景 | 推荐处理方式 | 是否需要外部通用 LLM |
|---|---|---:|
| 文本型 PDF | MinerU Flash/Basic 等解析，再进入结构化抽取 | 文档解析阶段通常不需要；需求理解阶段需要 |
| Markdown | 应用内 Markdown 解析器，再进入结构化抽取 | Markdown 解析阶段不需要；需求理解阶段需要 |
| 普通 DOCX | MinerU Office 原生解析，再进入结构化抽取 | 文档解析阶段通常不需要；需求理解阶段需要 |
| 扫描型 PDF | MinerU Basic OCR；按质量要求升级档位 | OCR 阶段不一定需要 VLM；需求理解阶段需要 |
| 复杂表格、公式和多栏版面 | MinerU Standard/Advanced，必要时启用 VLM | MinerU 内部可能需要 VLM；另外仍需要需求理解 LLM |
| 电机控制建模方案生成 | 规范模型 + LLM + 电机领域规则 | 需要 |

这里的“需要 LLM”有两个可能含义，应在架构中分开：

1. **MinerU 内部的 VLM：** 用于复杂文档视觉理解，不等同于业务 LLM；
2. **业务语义 LLM：** 用于把文档内容转换为控制系统需求和 Simulink 方案，这是本项目的核心智能环节。

因此，首版不建议把所有文档都送入最高成本的 VLM。可以按文档质量分流：先做原生文本和轻量解析，检测到扫描页、复杂表格、公式图片或版面异常时再升级解析档位；解析完成后，再把结构化片段交给业务 LLM。

#### 对原计划的影响

引入 MinerU 后，技术架构中 PDF/DOCX 的“文档解析”和“OCR”可以具体化为 MinerU 适配器，Markdown 仍由应用内解析器处理；不能因此删除业务 LLM 预算。预算应拆成：

- MinerU 本地运行的 CPU/GPU、模型下载和部署成本；
- 复杂文档使用 VLM 的推理资源；
- 需求结构化、领域推理和方案生成的 LLM 调用成本；
- 规则校验、人工确认和回归评测成本。

项目 PoC 应至少比较三条链路：

1. MinerU Flash/Basic 解析 + 业务 LLM；
2. MinerU Standard/Advanced（含 VLM）解析 + 业务 LLM；
3. 解析失败或低置信度时的人工确认流程。

比较指标包括：关键参数召回率、公式和单位正确率、来源追踪完整度、端到端耗时、CPU/GPU 内存与推理成本、业务 LLM 调用成本和人工修订量。MinerU 当前文档说明 Basic 可运行于 CPU，Standard/Advanced 的速度和内存需求取决于 VLM 引擎、输入规模和并发；PoC 应在目标部署硬件上实际测量。

## 5. 开发模型建议

### 5.1 推荐模式

采用 **阶段门控的双周敏捷开发 + DevOps**。

每两周形成一个可演示增量，同时在关键节点设置技术和质量门。这样既能快速验证不确定的解析和识别能力，又能避免在结果不可追溯时继续堆叠页面功能。

### 5.2 为什么不采用纯瀑布

纯瀑布要求早期完整确定需求，但本项目的以下因素存在明显不确定性：

- 用户文档格式差异大；
- 扫描 PDF、公式和表格识别效果需要实测；
- 不同电机模型的表达方式不统一；
- 用户确认页的交互需要真实试用反馈；
- 大模型输出质量需要通过样本文档校准。

### 5.3 为什么不采用无阶段门的敏捷

完全依赖迭代容易出现：

- 页面开发完成，但核心抽取准确率不达标；
- 模型图、参数表和报告来自不同逻辑；
- 规则和提示词不断变化，历史结果无法复现；
- 为了“看起来支持更多领域”而牺牲可靠性。

### 5.4 DevOps 质量机制

每次合并代码建议执行：

- 单元测试；
- API 和异步任务测试；
- 规范模型 Schema 校验；
- 代表性文档回归测试；
- 导出文件一致性检查；
- 模型结构图视觉回归检查；
- 敏感数据和依赖漏洞扫描。

每个生成结果保存以下元数据：

- 文档版本；
- 用户配置版本；
- 解析器版本；
- 领域规则版本；
- 提示词版本；
- 大模型版本；
- 规范模型快照。

## 6. 主要风险与应对

| 风险 | 概率 | 影响 | 应对措施 |
|---|---:|---:|---|
| 文档格式复杂，OCR 或公式识别不稳定 | 高 | 高 | MVP 先限制文本和表格；失败内容明确标注解析状态 |
| 大模型错误补全参数或结构 | 高 | 高 | 领域模板、规则校验、置信度、人工确认和禁止静默猜测 |
| 电机模型表达方式差异大 | 中高 | 高 | 先覆盖有限模型族，建立明确的“不支持”边界 |
| 图、表和报告内容不一致 | 中 | 高 | 所有导出物来自唯一规范模型，并增加一致性测试 |
| 缺少真实验收文档 | 高 | 高 | 第 1 周建立至少 30～50 份脱敏文档集和参考答案 |
| Simulink 模块名称或参数不兼容 | 中 | 中高 | 建立 R2025b 模块目录并进行版本化测试 |
| `.m` 代码生成造成执行风险 | 中 | 高 | 仅生成模板代码；默认不执行；限制文件和命令操作 |
| API 成本或响应时间不可控 | 中 | 中 | 缓存、批处理、模型分级和供应商抽象 |
| 用户误认为系统已完成仿真验证 | 中 | 高 | 报告明确区分输入、推断、建议和验证结果 |
| 工程文档泄露 | 中 | 高 | 加密存储、访问控制、保留期限和本地部署选项 |
| 范围持续扩张 | 高 | 高 | 以 MVP/P1/P2 分层，所有新增领域通过阶段门进入 |

## 7. 质量目标与验收建议

以下指标建议在 PoC 阶段用实际样本文档校准，作为 MVP 目标：

| 指标 | 建议目标 |
|---|---:|
| 文本和表格关键字段识别准确率 | ≥95% |
| 电机控制关键实体识别 F1 | ≥0.85 |
| 关键连接关系识别 F1 | ≥0.85 |
| 关键参数来源追踪覆盖率 | ≥95% |
| 缺失关键参数显式标注率 | 100% |
| 推断内容置信度和来源标注率 | 100% |
| 图、表和报告一致性 | 100% 通过自动校验 |
| 同输入重复生成的语义一致性 | 100% 通过规范模型比较 |

“同一输入生成一致”应定义为语义一致，而不是要求大模型输出文本字节级完全相同。系统应保存文档、提示词、模型、规则和规范模型版本，以支持复现和问题定位。

### 7.1 建议验收样例

验收至少应包含：

1. 一份包含直流电机速度闭环的文本型 DOCX；
2. 一份包含参数表的 PDF；
3. 一份包含缺失参数和单位问题的 Markdown；
4. 一份扫描型 PDF，用于验证 OCR 低置信度标记；
5. 一份存在歧义或内部矛盾的文档；
6. 一份包含公式和初始条件的文档。

### 7.2 验收结果

给定直流电机速度闭环文档，系统应能够：

- 识别给定值、误差、控制器、电机对象和反馈信号；
- 生成结构完整、可读的 Simulink 风格模型图；
- 列出推荐模块类型；
- 输出参数、单位、状态和来源；
- 输出完整的连线关系；
- 标注缺失电机参数和初始条件；
- 给出仿真时间、采样时间和观测信号建议；
- 允许用户修改解析结果；
- 保证图、表格和报告内容一致；
- 让用户能够在 MATLAB/Simulink R2025b 中按结果手动复现模型。

## 8. 交付物清单

MVP 每次生成一个方案包：

```text
建模方案/
├─ 需求解析结果.md
├─ Simulink模型结构图.svg
├─ Simulink模型结构图.png
├─ 模块清单.csv
├─ 模块参数表.csv
├─ 连线关系表.csv
├─ 仿真配置建议.md
├─ 假设与待确认项.md
└─ 文档来源追踪表.csv
```

如果生成 `.m` 文件，应在导出页面显式标注：

- 代码只用于辅助搭建；
- 代码未经自动执行；
- 代码是否适用于用户当前 MATLAB 环境需要用户确认。

## 9. 项目启动前置条件

正式投入完整 MVP 开发前，应完成以下事项：

1. 将“仿真结果判断”拆分为 MVP 静态检查和后续仿真数据分析；
2. 准备至少 30～50 份脱敏需求文档；
3. 为每份样本文档准备控制系统专家参考答案；
4. 明确首版支持的电机模型族和 Simulink 基础模块；
5. 确定云端模型、OCR 和数据存储的合规边界；
6. 确认 MATLAB/Simulink R2025b 的模块名称和参数规则；
7. 在第 2 周完成 PoC，并以 PoC 结果决定是否进入完整 MVP。

## 10. 最终建议

建议立项，但采用“先 PoC、后 MVP”的方式推进。

第一阶段不要追求覆盖所有控制领域，而应验证一个可靠闭环：

```text
典型电机控制文档
  → 可追溯需求结构
  → 用户可确认的模块和参数
  → 一致的模型图、参数表和连线表
  → 可供用户在 Simulink R2025b 中复现的建模方案
```

如果 PoC 能够在真实样本文档上稳定完成上述闭环，再按 14～16 周计划开发 MVP。后续扩展应以真实文档和验收数据驱动，逐步增加温控、液位、机械系统、仿真数据分析和 MATLAB 集成功能。
